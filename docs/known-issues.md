# 已知问题与待办

记录当前版本里**已知但不阻塞**的问题，以及已经确定的修复方向。

---

## 1. 书签恢复后「分组结构与原来不一致」

**现象**（0.60.2 起可复现）：

- `更多 ▾ → 恢复为 IDE 书签…` 能把全部书签按文件、行号、描述恢复出来（实测 458 条全部成功）
- 但恢复出来的 **Rider 书签列表（list）结构**和导入前不同：
  - 原列表的层级、命名、书签归属与恢复结果不完全一致
  - 部分书签落在新建的列表里，而不是原来的列表

**原因**：

导入时我们按「书签列表 → 同名分组」建组，并把列表名存进分组标题；
恢复时是用**分组标题**反推列表名（`manager.getGroup(name)` / `addGroup(name)`），
而分组标题在导入后被用户改过、或有同名分组时，就无法还原原来的列表归属。

**影响**：书签内容和位置正确，只有列表归属/层级需要人工整理。

**修复方向（专门流程）**：

1. 导入时把原始列表身份额外持久化（例如 `Anchor.sourceListId` / `sourceListName`），
   不要只依赖分组标题
2. 恢复时优先使用持久化的原始列表名，其次才用当前分组名
3. 导入时记录一份「导入批次」清单（批次 id、时间、每个锚点的原始列表），
   支持「按批次恢复」和「按批次撤销导入」
4. 恢复前先做一次 diff：列出将创建的列表/书签，让用户确认后再写入

**优先级**：中（数据不丢，只是结构要手工整理）

## 2. 顺序（schema 3 混排）

0.66.0 起组与锚点共用 `orderValue`，支持组拖到锚点中间。
**已验证**：迁移后列表顺序与迁移前一致（手动确认，2026-11-10）。
